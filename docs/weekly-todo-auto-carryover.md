# 未完了To Doの自動引き継ぎ（本番未反映）

現在の公開基点は `docs/production-current.md` の2026年10月22日版。今回の変更は準備中で、公開済みではない。

## 動作

日本時間の毎週月曜0時、従業員・管理担当者・社長それぞれの保存済み未完了項目を翌週の本人用下書きへ追加する。完了（進捗100％）・取り下げ済みは除外。最新の下書きがあれば共有版より優先し、共有していない項目も非公開のまま引き継ぐ。目標、進捗、実績、入力言語を保持する。

本人は「今週のTo Do」→「自分の入力」で目標を見直し、共有する。自動処理は共有版・初回目標・振り返り・共有履歴を変更しない。過去週も変更せず、日報メモの自動追加や通知送信は行わない。

## 実装

- 新規スケジュール処理 `automaticWeeklyTodoCarryover`。月曜0時、`Asia/Tokyo`、最大5回再試行。全有効プロフィールの対象権限を処理し、Auth無効化・非有効アカウントは除外。デモは環境別に分離する。個別失敗後も残りの利用者を処理し、最後に失敗を返して再試行する。
- 既存 `getWeeklyTodoWorkspace` から本人分の未処理を補う。過去週と未来週は変更せず、今週だけに実行する。複数週空いた場合は直近の保存週を採用する。
- Firestoreトランザクション内で現在のプロフィール、対象週、本人の週間文書を読む。単一フィールド `userId` の既存自動インデックスを使うため、新規複合インデックスは不要。利用環境は文書の `scopeId` で再照合する。
- 取り込み元の週と項目IDによる固定識別値・既存 `carriedSources` で重複を防ぐ。内容追加と待機状態が変わる場合だけ版番号を進める。編集中の古い版は既存の競合表示で入力を保持する。
- 30件・本文120KBを維持。超過分は新フィールド `carryoverPending` に `{ weekStart, itemId }` の配列として保存し、本文を複製しない。取得時に元の最新内容を再確認して追加し、待機分は翌週にも継承する。
- 旧選択式APIの応答フィールド `carryover` と保存互換性は保持。新画面では選択式の追加操作を表示しない。

## 配備対象と復旧

今回必要な反映対象は、新規 `automaticWeeklyTodoCarryover`、既存 `getWeeklyTodoWorkspace`・`saveWeeklyTodoDraft`・`shareWeeklyTodo`・`shareWeeklyTodoReview` の4処理、Hostingのみ。保存系の3処理では、引き継ぎ元のマップのキー順序が変わっても同じ元として比較できるようにする。日報・履歴・翻訳Callableは変更対象外。Rules、Secret、既存業務データ、共通お知らせのパッケージとCOCOは変更対象外。

配備前に最新の公開記録・現行配信・関数の設定を再照合する。新規スケジュールを有効にすると現在週の下書き追加が発生し得る。今回の準備中には実データへの試験保存や本番配備を行わない。

停止時は新規スケジュールを停止し、既存4CallableとHostingを直前版へ戻す。引き継がれた下書きは利用者の入力を含み得るため自動削除しない。旧保存形式と互換性を保つ。

検証はフロント・Functionsのテストと両ビルド、指定のApp・更新情報テスト、架空データの画面操作で行う。実Firestore・Cloud Scheduler・実機での受入は本番反映後の確認事項。
