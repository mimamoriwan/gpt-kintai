# 運用手順

## 目的と範囲

このシステムは、従業員の勤務実態と業務内容を日々の記録として残し、日報、週次レポート、定例会レジュメ、フィードバック、月次資料へつなげるために使用します。

中国語から日本語への変換は、入力済みの日報や商品記録を共有しやすくするための機能です。リアルタイム音声翻訳、商談録音、自動議事録作成は本システムでは行わず、`translate_app` で別に運用・開発します。

## 毎日の運用

1. 従業員は勤務形態を選択し、「始業」を押します。
2. 「日報」を開いて記録する日付を確認し、日中に行った業務をタグ付きの業務メモとして記録します。見積書・商品資料・写真・Webリンクなどがある場合は、メモを追加する前にその報告へ添付します。必要に応じて「商品候補」も登録します。
3. 業務終了時に業務メモから日報のAI下書きを作り、事実と一致するように確認・修正して提出します。AI下書きを作れない場合も手入力で提出できます。中国語本文は原文を保持し、日本語版を自動生成します。
4. 「終業」を押します。表示時間は休憩を控除していない経過時間です。
5. 打刻忘れや通信不良があった場合は、実時刻と理由を入力して訂正します。
6. 管理担当者は未提出・未退勤・再確認が必要な記録を確認します。

## 3人共有カレンダー

- ホームで日付を選び、通常予定、出張、休みを登録します。参加者は個別選択または「全員（3人）」で指定できます。
- 通常予定と出張は件名が必須で、開始・終了時刻とメモは任意です。すべての種類で開始日から終了日まで最大60日をまとめて登録できます。
- 休みは参加者名と期間だけを共有し、理由、メモ、時刻は保存しません。複数日予定の変更・削除は期間全体に適用されます。
- カレンダーの休みは予定情報です。勤怠実績、非勤務理由、有給残数、日報には反映されないため、実際に勤務しなかった日の記録は従来どおり別に登録します。
- 管理担当者は「管理」→「カレンダー名簿」で、3人の表示名、表示順、ログインとの紐付けを管理します。社長はログインしなくても参加者にできます。

### 予定勤務日に勤務しなかった場合

- 有給休暇、欠勤、病気・体調不良、特別休暇、会社指示による休業、その他から理由を登録します。
- 予定勤務日に始業記録も非勤務理由もない場合だけ、本人と管理担当者の確認対象になります。
- この記録は休暇残数、給与、割増賃金などを計算するものではありません。

## 会社休日と休日勤務

- 土日と日本の祝日は自動的に「会社休日（予定）」として表示されます。会社独自の休日や振替出勤日は、管理画面の「会社カレンダー」から管理担当者が例外登録します。
- 会社休日に勤務しない場合、始業・終業の操作は不要です。休日予定だけでは勤怠記録や勤務日数は作成されず、未打刻警告も表示されません。
- 急な会議や顧客対応が入った場合は「休日業務を開始」を押し、確認後に勤務形態を選んで始業します。会社休日の予定は消えず、実績側に「休日勤務」と記録されます。
- 休日勤務でも終業打刻と日報提出は通常どおり必要です。
- このシステムは休日割増、残業、法定休日、給与を判定・計算しません。必要な扱いは就業規則と社労士の確認に従ってください。

### 会社カレンダーの例外登録

1. 管理画面で「会社カレンダー」を開きます。
2. 開始日と終了日を選ぶと、開始日の土日祝に基づく自動判定が表示されます。1日だけの場合は両方を同じ日にします。
3. 平日を休日にする場合は「会社休日」、休日を出勤日にする場合は「通常出勤日」を選び、必要に応じて「夏季休業」などの名称を入力して保存します。
4. お盆や年末年始は期間で一括登録します。中国の旧正月は自動判定されないため、会社全体が休む場合だけ会社休日として登録します。
5. 自動判定へ戻す場合は、一覧から期間の例外設定を削除します。後から個別に上書きした日は別の設定として残ります。

## 毎週の運用（月曜日を想定）

1. 従業員が「業務サイクル」→「週次計画・レポート」で「今週の計画」を入力します。管理担当者が内容を確認し、確定します。
2. 管理担当者は前週分の日報を確認済みにします。未確認日報が残っていても週次レポートの下書きは作れますが、最終確定はできません。
3. 「業務サイクル」→「週次計画・レポート」で、前週の月曜日から日曜日を対象にAI週次レポートを作成します。
4. AI下書きを管理担当者が事実確認・編集して確定します。AIが使えない場合は手入力で作成します。
5. 定例会で、前週の振り返り、中国市場の情報、決定事項、今週の目標、担当者と期限を記録します。

日報のAI下書きを作成するときは、その日の業務メモとタグ、および業務メモへ保存した写真・PDF・Word・ExcelをOpenAI APIへ送信します。URLリンクは自動取得しません。添付資料は内容確認のための一時入力として扱い、Responses APIのアプリケーション状態として保存しない設定（`store: false`）で送信します。生成後は必要な日報下書きだけをFirestoreへ保存します。同じ日・同じ入力内容ではこの保存済み下書きを返し、OpenAI APIを再実行しません。当面はAI生成の回数上限を設けず、管理画面の月別・利用者別の利用回数を確認して今後の制限要否を判断します。

日報AIが1日に確認できるファイルは最大10件・合計20MBです。PDFと画像は低詳細度で処理し、資料内の指示文は命令として扱わず、対応する業務メモの根拠資料としてだけ参照します。週次レポートのAIへ送るのは、日報本文、業務メモとタグ、週次計画、商品候補の文字情報、勤怠の集計値だけで、写真、添付文書、Google Driveの申請資料は送信しません。

業務メモの添付は、1件の報告につき最大5件・合計20MBです。ファイル本体はCloud Storage、どの報告に紐づくかという情報はFirestoreへ保存します。過去に日報全体へ添付した資料は削除せず、既存資料として保持します。

## 成果物・やり取りの保存

- 見積書、商品調査資料、メーカー資料、商談記録、契約書、取引先メール、社内連絡、会議議事録など、後から業務実態を説明する資料は会社のGoogle Driveへ保存します。
- 管理担当者は「業務サイクル」→「関連資料」で、対象者、資料名、種別、日付、関係者、Drive URL、説明、公開範囲を索引登録します。
- ファイル本体をFirebaseへ重複保存せず、長期保管する原本は会社のDriveを正とします。
- 雇用・在留関係の機密文書は管理担当者と社長だけが閲覧できる区分で登録します。

## 毎月の確定作業

1. 管理担当者が「業務サイクル」→「月次資料」で対象者と対象月を選び、JSON・CSV・添付一覧・印刷用HTMLを出力します。
2. 印刷用HTMLをブラウザで開き、「印刷」からPDFとして保存します。
3. JSON、CSV、添付一覧、PDFを会社のGoogle Driveへ保存します。
4. PDFのDrive URLをアプリに登録すると、その月の確定版として版番号と確定日時が記録されます。
5. 確定後に勤怠、日報、業務メモ、週次計画、週報、会議、商品候補、非勤務理由、関連資料が変更されると「新版の再出力が必要」と表示されます。
6. 新版を作成してURLを登録すると、以前の版は削除されず「旧版」として残ります。

月次資料には、実勤務、会社休日・休日勤務、非勤務理由、訂正、日報原文と日本語版、業務カテゴリ、業務メモ、週次計画、週次レポート、会議、商品候補、関連資料索引が含まれます。法的な労働時間、休憩、賃金、在留資格適合性は判定しません。

## 雇用・職務基準

- 管理担当者は、行政書士確認済みの職務区分を登録し、会社共通業務カテゴリと関連付けます。
- 個人タグは日々の整理用、会社共通業務カテゴリは正式な活動分類として使います。
- 職務内容説明書、申請理由書、労働条件通知書兼労働契約書、在留資格認定証明書交付申請書などは、文書名・Drive URL・作成日・確認日・用途だけを登録します。
- システムとAIは在留資格への適合性を判定せず、活動分布と未分類件数を確認材料として表示します。

## 在留更新準備

- 管理担当者専用画面で、在留期限、行政書士への確認予定日、入管案内の最終確認日、準備項目、担当者、証拠URLを管理します。
- 在留期限の120日前、90日前、60日前にはアプリ内で準備時期を表示します。
- 必要書類はシステムが確定せず、申請時点の出入国在留管理庁の案内と行政書士の確認結果に合わせて更新します。
- 本システムの出力は勤務実態・活動内容を説明する補足資料であり、更新許可や提出資料としての採用を保証しません。

## その他の定期作業

- 毎月: Firebase、Storage、Functions、OpenAIの利用量と請求額を確認します。
- 退職・長期停止時: アカウントを削除せず無効化し、既存記録を保持します。
- 記録は最低5年間保持し、自動削除しません。

## AI利用費の初期想定

- gpt-kintaiのOpenAI API費用は、初期運用では月額最大10 USDを想定します。10 USDの定額契約ではなく、実際の利用量に応じて請求される従量課金の上限想定です。
- この金額にFirebase、Cloud Storage、Hosting、Functions、Google Drive、将来のCOCO共通基盤や他システムのAI費用は含みません。COCO全体の費用計画では別項目として積算します。
- 同一入力内容の下書き再利用と1日最大10ファイル・合計20MB制限を継続します。日報AIの生成回数には当面上限を設けず、管理画面で月別・利用者別・日時別のAPI生成回数、保存済み下書きの再利用回数、対象の日報日、入力・出力トークン数、添付資料数を確認します。月間のAPI生成が50回に達した場合は、管理担当者のホームと管理画面に警告を表示し、運用実績から今後の利用基準を見直します。
- 稼働後1〜3か月の実績を確認し、利用者数、生成回数、添付資料量、トークン数に応じて10 USDの想定を見直します。
- OpenAIの専用プロジェクト `gpt-kintai` には、月額10 USDのProject spend limitと「Enforce a hard limit」を設定済みです。上限到達後はAPIリクエストが失敗します。ただし利用額の反映と停止は即時ではないため、最終請求額が10 USDをわずかに超える可能性があります。

## デモ運用の終了

方さんの実演用データとデモ用認証アカウントは本番Firebaseから削除済みです。管理担当者・社長画面の「デモデータを表示」も廃止し、画面は通常の本番データだけを表示します。

削除日時と対象データセットを確認できるよう、`demoDatasets` の削除済み管理記録だけは監査用に保持します。デモ識別情報によるデータ分離と削除時の安全確認処理は、過去データの誤混入を防ぐため内部に残します。本番環境へデモデータを再投入する場合は、あらためて明示的な運用判断と事前確認を必要とします。

## 修正記録

提出後の修正では旧内容、修正者、日時、理由が履歴に残ります。管理担当者は本人の原文を上書きせず、内容を確認済みにします。修正後は再確認が必要です。

## 在留期間更新前

このシステムは勤務実態の説明に役立つ日常記録を蓄積しますが、更新許可や資料採用を保証しません。申請前に、行政書士の助言、出入国在留管理庁の最新案内、雇用契約・就業規則に関する社労士の確認を改めて行ってください。
