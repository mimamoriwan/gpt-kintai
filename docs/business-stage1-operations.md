# 「会社の取り組み」第1段階の公開・運用手順

2026年9月16日。対象は工程表、テーマ・取り組み、担当・状態・節目、近況、変更履歴、共有メンバー設定、お知らせ作成への入口、日本語・中国語表示である。この文書は実装された処理に基づく手順であり、検証環境への配置、本番公開、公開後の観察が完了したことを示すものではない。

第2段階の業務メモ共有は含まない。`setBusinessWorkLogLink`、`listBusinessSharedMemos` は今回の公開対象ではなく、業務メモ・日報への項目追加、添付の共有、日報自動処理の変更も行わない。工程表の棒は予定期間、節目の「2/3」は完了した節目数を表す。工数・作業量の進捗率、自動遅延判定、Excel取込、COCO連携は実装範囲外である。

## 有効化と共有メンバー

| 設定 | 場所・判定 | 無効時の動作 |
|---|---|---|
| `VITE_BUSINESS_FEATURE_ENABLED` | 画面のビルド時環境変数。文字列 `true` の場合だけ有効 | メニュー・専用画面を開かない。取り組みへのリンクからも利用できない |
| `BUSINESS_FEATURE_ENABLED` | 新設Functionsの実行環境変数。文字列 `true` の場合だけ有効 | 全11窓口を `failed-precondition` で停止する。共有設定の取得・再開操作も不可 |
| 共有設定の `enabled` | `businessSettings` に保存する設定 | 取り組み・近況・履歴・翻訳の通常操作を停止する。共有メンバーには停止状態を返し、共有中の管理担当者・社長は設定を再開できる |

両環境変数は、未設定・空文字・`false`・`TRUE` などでは無効となる。画面側の変更には再ビルドとHosting公開が必要であり、サーバー側の変更には対象Functionsへの設定反映が必要である。画面のフラグだけでは、既に開いている画面からの要求を停止できない。

初回は共有設定が存在しないため、通常の読み書きはできない。現在の有効な `employee_manager` または `president_viewer` のアカウントだけが、初期設定に必要な候補一覧を取得して共有メンバーを登録できる。登録は次の手順で行う。

1. 検証済みの新画面へヤスシさんまたは社長が本人のアカウントでログインし、「共有メンバー設定」を開く。
2. 既存アカウントからヤスシさん・社長・方さんの3名を明示的に選択する。表示名だけで判断せず、設定時に本人のアカウントと対応していることを確認する。
3. 共有を有効にして保存する。初回の設定版は `0`、保存後は `1` となる。設定は現在の版を照合して保存する。
4. 3名それぞれの表示と権限を確認する。最初のテーマ・取り組みは実際の方針に基づき手動登録する。画面見本や検証用の架空データを本番の進捗として登録しない。

登録人数は重複のない3名に限定する。操作する管理者本人、管理担当者ロール、社長ロールのアカウントを含む必要がある。無効・停止中のアカウントや別デモ範囲のアカウントは保存時に拒否する。新規社員は自動で共有メンバーに加わらない。CBC麻布台とCBC寧遠の会社名による利用者・権限の分離はない。

この機能では、ヤスシさんと社長が同等の管理権限を持つ。登録・構成変更・担当変更・全件の状態変更・節目の構成変更・アーカイブ／復元・共有設定を直接行える。方さんは閲覧、自分の近況投稿、自分が担当する取り組みの状態・節目完了の変更ができる。既存の日報・勤怠・お知らせの権限は変更しない。

## 公開対象の11窓口

すべて `asia-northeast1` のCallable Functions。実環境ではApp Checkを必須とし、サーバーは有効なAuthアカウント、現在のプロフィール、共有メンバー、停止設定を確認する。管理権限は現在の `users` のロールで判断し、画面のボタン表示だけに依存しない。

| 公開名 | 用途・操作権限 |
|---|---|
| `getBusinessWorkspace` | 共有設定、テーマ、取り組み、担当者候補等の取得。初期設定・停止時には限定した情報を返す |
| `getBusinessInitiativeDetail` | 閲覧可能な取り組みの近況・変更履歴を取得。ページ送りに対応 |
| `getBusinessHistory` | テーマの履歴を取得。共有メンバー設定の履歴は管理担当者・社長だけが取得 |
| `saveBusinessTheme` | 管理担当者・社長によるテーマの登録・編集・表示順変更 |
| `saveBusinessInitiative` | 管理担当者・社長による取り組みの登録・構成・担当・予定期間等の変更 |
| `setBusinessArchived` | 管理担当者・社長によるテーマ・取り組みのアーカイブ／復元 |
| `postBusinessUpdate` | 共有メンバー本人の近況投稿。同じ投稿ID・同じ内容の再送を重複登録しない |
| `setBusinessStatus` | 管理担当者・社長は全件、方さんは担当する取り組みの状態変更 |
| `setBusinessMilestoneCompletion` | 管理担当者・社長は全件、方さんは担当する取り組みの節目完了／取消 |
| `saveBusinessSettings` | 管理担当者・社長による3名の共有メンバー指定と共有の停止／再開 |
| `translateBusinessContent` | 閲覧可能なテーマ・取り組み・近況の現在の原文を翻訳 |

変更は読み込んだ版を照合し、変更と履歴を同じトランザクションで保存する。節目は名前や配列順に依存しないIDで指定し、反転要求ではなく希望する完了値を渡す。同値の再送でも現在の権限・担当・アーカイブ状態を確認し、更新日時・履歴を重複させない。

翻訳は原文保存と別処理であり、失敗しても原文は残る。既存の `OPENAI_API_KEY` Secretを参照するのは `translateBusinessContent` だけである。新しい鍵の作成・既存鍵の変更はこの公開手順に含めない。秘密値を確認記録・コマンド引数・ログへ記載しない。翻訳結果は原文の版と言語で再利用するが、キャッシュ利用時にも現在の閲覧権限と原文の版を確認する。

`businessSettings`、`businessThemes`、`businessInitiatives`、`businessUpdates`、`businessHistory`、`businessTranslations` は、管理担当者・社長を含むブラウザからの直接読取・書込をRulesで禁止している。既存APIの名前・入力出力・保存形式は変更しない。

## 検証環境と公開の順序

検証環境の架空アカウント・架空データで確認し、合格した同一ソースコミットを公開候補とする。環境別のビルド結果は別々に保持する。現作業ツリーの `firebase.json` のHostingサイトは本番 `gpt-kintai` であり、検証環境へそのまま流用しない。

検証環境は `gpt-kintai-staging` を明示指定し、Hostingサイト・Functions・Firestoreを同じ検証プロジェクトに向けた専用の配置設定を確認する。既定プロジェクトやエイリアスの暗黙の選択に頼らない。共用の検証環境は引継ぎを確認してから利用し、他改修と並行で配置しない。

1. **公開候補と退避先を確定する。** 元の未公開変更を取り込まず、既に本番公開された改善を含む確定コミットを使用する。コミット、環境別成果物、直前のHosting版、配置対象を公開台帳に記録する。
2. **新サーバー処理・追加Rules・追加indexを先に配置する。** 画面側フラグは無効のままとする。新規11 Functionsだけを対象にし、既存Functionsを再配置しない。Rulesとindexはファイル全体が配置単位なので、既存ルール・既存indexが保持され、今回の追加だけであることを差分で確認する。対象外indexの削除を伴う配置は行わない。
3. **サーバーの無効・有効双方を確認する。** 未設定／無効時には全11窓口が停止することを確認する。有効時には有効アカウント、共有範囲、両管理ロール、担当者制約、原文版検査が働くことを確認する。新しいindexの準備完了を待つ。
4. **画面を有効にした候補を確認する。** `VITE_BUSINESS_FEATURE_ENABLED=true` でビルドした画面を使用し、初期3名設定と受入項目を確認する。本番への初回画面公開後も、3名の設定を有効にするまでは通常データの操作はできない。
5. **本番は手動で対象を限定して配置する。** 検証結果を整え、公開直前に本番基点と他改修の有無を再確認する。サーバー・Rules・index、稼働確認、画面の順で実施する。新しい画面を配信した後は、既存の手動更新案内で利用者が入力を保存・退避してから切り替える。

本番の新Functionsだけを指定する形式は次のとおり。これは実施時の対象確認用であり、文書の作成により実行・公開されたものではない。`BUSINESS_FEATURE_ENABLED` の変更を反映する場合も、同じ11窓口に限定する。

```sh
firebase deploy --project gpt-kintai --only "functions:getBusinessWorkspace,functions:getBusinessInitiativeDetail,functions:getBusinessHistory,functions:saveBusinessTheme,functions:saveBusinessInitiative,functions:setBusinessArchived,functions:postBusinessUpdate,functions:setBusinessStatus,functions:setBusinessMilestoneCompletion,functions:saveBusinessSettings,functions:translateBusinessContent"
```

```sh
firebase deploy --project gpt-kintai --only "firestore:rules,firestore:indexes"
```

```sh
firebase deploy --project gpt-kintai --only hosting
```

Functionsの環境変数は対象プロジェクトのFunctions環境設定に置く。例えばプロジェクト別の環境ファイルを利用する場合は `functions/.env.gpt-kintai` と `functions/.env.gpt-kintai-staging` を分ける。画面側の `VITE_` 環境変数をFunctionsの設定として扱わない。全体を対象とする `firebase deploy` や `--only functions`、削除を自動承認するオプションは使用しない。既存の本番Functions、Storageルール、認証設定、Secret、既存業務データは今回の対象外である。

## 受入記録と3営業日の観察

ローカルの型検査・自動試験・Auth／Firestoreエミュレーター確認は、実クラウドのCallable通信、App Check、本番アカウントの表示確認の代わりにはならない。検証環境への配置と実接続確認を実施していなければ「未実施」と記録する。

公開前は少なくとも次を確認し、使用した環境、アカウントのロール、候補コミット、結果を残す。

- ヤスシさんと社長の両方による登録・編集・構成変更・担当変更・アーカイブ／復元・共有設定。方さんの管理操作拒否と担当する取り組みの状態・節目更新。共有外のアカウントの拒否。
- 工程表と一覧の一致、単月・年越し・期間未設定、節目未設定、節目の追加・並べ替え・アーカイブ・取消。状態と節目の完了が相互に自動変更されないこと。
- 同時編集の競合、通信失敗、他者更新中の入力保持、ログアウト・アカウント切替・共有解除後の表示。取得失敗を空一覧と区別すること。
- 日本語・中国語、原文保存、翻訳失敗からの再試行、古い翻訳の拒否、キャッシュ取得時の認可。
- 取り組みからのお知らせ作成、既存下書きの保持・切替確認、本人による宛先・本文確認後の発信、通知から取り組みへのリンク。未確認・返信・対応完了を既存どおり確認し、取り組みの状態を自動変更しないこと。
- 既存の打刻、日報保存・AI作成、お知らせ、資料閲覧、手動更新の回帰確認。

本番公開後は3営業日、通常利用を観察する。日時の経過やタスクの完了表示だけでは合格としない。利用実績がない項目は「未確認」のまま残し、特別な架空の業務データを本番へ作って実績の代わりにしない。

| 観察対象 | 記録する内容 |
|---|---|
| 原文保存・近況・状態・節目更新 | 操作の利用件数、成功・失敗、重複、入力消失の有無 |
| 権限 | 許可された操作の予期しない拒否、共有外・担当外操作の拒否 |
| 翻訳 | 原文の利用可否、翻訳失敗・再試行、古い訳の誤反映の有無 |
| 既存の主要操作 | 打刻・日報・お知らせ・資料・更新への影響 |
| 利用者報告 | 発生時刻、画面、操作、エラー、入力保持・復旧結果。必要な範囲で記録 |

観察開始・終了日、各日の実績、残る未確認事項、最終判断を公開台帳に記載する。社長とヤスシさんが同等に管理でき、3名が近況を共有し、社長が確認・指示を出せることを受入条件とする。観察が未了の状態で次の改修の公開完了を扱わない。

## 停止と復旧

問題が起きた場合、登録内容を削除せず、新機能の操作を止める。

1. 管理画面が使用できる場合は、共有メンバー設定の `enabled` を無効にして保存する。共有中のヤスシさんと社長のどちらも操作できる。通常の書込・詳細取得・翻訳が停止し、両管理者は設定を再開できる。
2. サーバー窓口全体を停止する必要がある場合は、`BUSINESS_FEATURE_ENABLED=false` を新規11 Functionsにだけ反映する。この場合は設定窓口も停止するため、再開には運用担当によるサーバー設定の復旧が必要となる。
3. 画面の入口も停止する場合は `VITE_BUSINESS_FEATURE_ENABLED=false` の成果物を配置する。既に取得済みの内容は端末に一時的に残り得るため、画面の非表示だけをサーバー停止の代用にしない。既存の手動更新手順に従い、入力を保存・退避してから更新する。
4. 必要に応じてFirebase Hostingの公開履歴から、公開直前に記録した画面版へロールバックする。作業開始時点の本番版は **`97d6916bc03c0459`**（9月14日のお知らせ改善を含む）。実際の公開前に別の改善が追加されていれば、この番号を固定の復旧先として使用せず、最新の直前版と基点を更新してから公開する。
5. 復旧後はログイン、ホーム、打刻・日報・お知らせ・資料の主要操作と手動更新を確認する。新機能の再開は、原因修正を検証環境で確認してから行う。サーバー・共有設定・画面の3つの有効状態を再確認する。

Hostingを戻しても新機能のデータは削除しない。新Functionsを未設定・停止状態で残し、既存Functionsを過去版へ戻す操作は行わない。テーマ、取り組み、近況、変更履歴、翻訳結果、既存の日報・勤怠は保持する。復旧のために共有外へのアクセスを許可したり、App Checkを無効にしたりしない。

## 実装の参照先

- 窓口の公開・App Check・翻訳Secret: `functions/src/business/index.ts`
- 有効アカウント・共有・権限・版・停止・翻訳キャッシュの検査: `functions/src/business/service.ts`

- ローカル限定のAuth／Firestore確認: `scripts/verify-business-emulator.cjs`
