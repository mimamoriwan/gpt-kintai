# お知らせの端末通知

この文書は実装候補の設定・試験・公開手順です。実装済みであることと、本番の通知が利用可能であることは区別します。

## 動作

新規 `presidentInstructions` の作成だけを `notifyNewAnnouncement` が検知します。返信、翻訳、確認、完了、取消、既存の再通知操作では発火しません。「取消して再発信」は別IDの作成なので対象です。保存と通知は独立しています。

対象は保存された宛先の実アカウントで、本人が有効化した各端末です。投稿者・無効アカウント・デモアカウントを除きます。端末登録時の認証時刻も保存し、パスワード変更で再認証が必要になった登録は送信対象にしません。登録前の投稿は遡って通知しません。通常の認証復旧では勝手にOFFにしません。

通知は日本語・簡体字の固定文だけです。本文・件名・添付・投稿者は送らず、通知先IDとお知らせIDを使います。URLに利用者ID、登録情報、業務本文は含めません。タップ時は既存のログインゲートとFirestoreの閲覧権限を通し、対象を開きます。タップだけでは確認済みにしません。

## Firebase設定（環境ごと）

1. 対象プロジェクトのFirebaseコンソール「プロジェクトの設定」→「Cloud Messaging」→「ウェブプッシュ証明書」でWeb Push鍵ペアを作成、または既存の鍵を使います。秘密鍵はフロントや作業記録に書きません。
2. **公開鍵だけ**をビルド用の環境ファイルへ `VITE_FIREBASE_VAPID_KEY` として設定します。既存のFirebase Web設定・App Check設定を引き継ぎ、環境のプロジェクトを混在させません。鍵がないビルドは設定画面に「準備中」と表示します。
3. FCM Registration APIとFirebase Cloud Messaging APIの有効状態を確認します。新しい送信関数の実行アカウントには、対象プロジェクトへのFCM送信に必要な最小権限を付けます。既存のアカウント鍵の配布・権限の一括変更は行いません。
4. サーバー専用ドキュメント `announcementPushConfig/default` に `{ enabled: false, allowedUserIds: [] }` を準備します。初期状態・文書がない状態では送信しません。管理者が検証対象UIDを明示して `enabled: true` にします。まず所有者本人1名、その後に受入対象3名へ広げます。停止時は `enabled: false` に戻します。
5. 次の新規関数だけを対象指定で配備します。`registerAnnouncementPushDevice`、`unregisterAnnouncementPushDevice`、`testAnnouncementPushDevice`、`notifyNewAnnouncement`。既存Functions・COCO認証ゲート・Rulesを旧版に戻さないでください。
6. 指定テスト・両ビルド・現行配信の再照合後、同じ候補のHostingを配備します。旧作業フォルダーの `dist` を使いません。アプリは既存の更新案内から本人が最新版へ切り替えます。

参考: [FCMのWeb設定](https://firebase.google.com/docs/cloud-messaging/js/client)、[iPhoneのWeb Push](https://webkit.org/blog/13878/)。

## 保存情報・認可

サーバー専用コレクションは `announcementPushDevices`、`announcementPushTokenOwners`、`announcementPushDeliveries`、`announcementPushConfig` です。現行Rulesの既定拒否でクライアントからの直接読み書きを禁止します。公開前に現行配備Rulesでも拒否されることを確認します。既存Rules全体をこの候補から公開しません。

登録・更新とテスト送信は既存の業務認証ゲートとApp Checkを必須とします。利用者IDはログイン情報から決めます。端末IDの乗っ取りと同一FCM登録情報の重複登録を拒否します。

**ログアウト後の解除だけは、端末固有のランダム256bit解除キーによる認証を使用します。** App Checkも必須です。このキーでできることは、その1端末の削除だけです。登録・閲覧・送信・他端末の削除には使えません。サーバーにはハッシュだけを保存し、端末内のIndexedDBで未完了解除を保持します。これにより、オフラインでログアウトしてログイン情報を失った場合にも再接続時の解除が可能です。解除キー・FCM登録情報はログやUIに出しません。

端末をOFFにするとIndexedDBの受信状態を先に無効化し、解除情報を保存します。サーバー解除に失敗してもOFF状態を維持します。再接続で再試行し、再有効化前には未完了の解除を完了します。アカウントが変わった端末を自動でONにしません。

## 配信・障害

- 投稿と端末ごとの送信記録、トランザクションの2分リース、端末側の通知IDで重複を抑えます。外部送信と記録の更新は原子的ではないため、配信を厳密な1回とは保証しません。
- iPhoneで受信権限が取り消されないよう、実際のPush受信では必ず表示処理を行います。同じIDの再配信は同じタグで置き換えて無音にし、通知を既に消していた場合には通知欄へ戻ることがあります。アプリ内部での重複処理は表示しません。
- Functionsのイベント再試行を利用し、一時的な送信エラーだけ再試行します。受理済みの端末へは再送しません。24時間を過ぎた投稿は停止し、FCMのTTLも残り時間に制限します。
- 無効なFCM登録情報を削除します。端末情報が更新されていた場合は新しい登録を削除しません。
- テスト送信は本人の1端末だけ、1分間隔です。「送信受付」と端末への到達を区別します。エラーログには投稿ID・分類・結果だけを出し、本文や送信先トークンは出しません。
- Web Pushは集中モード・OS設定・回線などに従います。緊急連絡の到達保証には使いません。既存の未確認件数と確認ボタンを併用します。

## 実機受入

3名のiPhoneごとにiOS 16.4以降、ホーム画面からの起動、通知許可を確認します。設定→テスト受信→他者からの宛先限定投稿→ロック中・閉じた状態での受信→タップ後の対象表示→OFFを試します。Wi-Fi・モバイル回線・通知拒否・ログアウト・アカウント切り替えも確認します。iPad・PCは代表環境で補助確認します。

端末OS、確認日時、環境、結果を記録します。管理者の送信ログだけで「受信できた」と判定しません。実機の受入結果が揃うまでは受入完了としません。
