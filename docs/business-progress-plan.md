## 1. 目的と範囲

会社の課題・目標と、誰が何に取り組み、設定した節目のどこまで完了したかを社長・管理担当者・方さんの3人で把握する。テーマと個別の取り組みの2段階で整理し、名称は「会社の取り組み」とする。工程表で全体を見渡し、必要な行を選んで近況確認・指示へ進む。

CBC麻布台・CBC寧遠による利用者や権限の分離は設けない。必要な会社の区別は説明に記載する。COCOは要件定義前であり、当面gpt-kintaiの一機能として運用する。

工数、作業量を表す進捗率の入力・推定、自動遅延判定、工程間の依存関係、予算・在庫・受発注、COCO連携、Excel自動取込は今回の対象外。今回追加する「2/3」等は設定した節目の完了数であり、工数・作業量の67%を意味しない。

## 2. 第1段階

### 画面とデータ

| 対象 | 内容 |
|---|---|
| テーマ | 名称、目的・説明、表示順、参考資料リンク |
| 取り組み | 所属テーマ、名称、説明、担当者、状態、予定開始・終了月、目標時期メモ、参考資料リンク |
| 取り組み内の節目 | 安定した識別子、名称、表示順、完了・未完了、変更者・変更日時、アーカイブ状態 |
| 近況 | 投稿者、投稿日時、短い報告本文 |
| 履歴 | 変更者、変更日時、変更前後の担当・状態・説明など |

- 担当者は複数選択可、未定可。「担当未定」を一覧表示する。
- 状態は未着手・取り組み中・保留・完了。細かな理由入力を必須にしない。
- 工程表を初期表示とする。横棒の位置・長さは予定期間、色と文字・アイコンは既存4状態、別欄の点と「完了数 / 全数」は節目の到達状況を表す。予定期間の経過を実績の進捗として描かない。
- 予定期間は月単位の開始・終了を指定し、どちらも未設定を許容する。未設定は「期間未設定」と明示し、一覧から除外しない。目標時期の自由メモも残し、「9月末」などの補足に使う。自由メモから日付を自動推定しない。
- 節目は取り組みに必要なものを少数ずつ登録する。未登録は「節目未設定」と表示する。全節目の完了と取り組みの状態は別々に更新し、お知らせの対応完了とも連動させない。
- 一覧は名称・担当・状態・最新近況・最終更新日を表示し、テーマ・担当・状態で絞り込む。
- 「工程表」と「一覧・近況」を切り替えても、同じ取り組み・担当・状態を参照する。行選択から節目・近況・お知らせの入口を開ける。
- 完了後も履歴を保持する。不要な項目は物理削除せずアーカイブし、復元可能にする。
- 受信データと編集フォームを分離する。同じ項目への同時編集は版を照合し、競合を通知して無言の上書きを防ぐ。

既存のemployee_managerとpresident_viewerを、この機能では同等の管理権限として画面・サーバー双方で判定する。他機能のロールや権限は変更しない。通常の登録は管理担当者が行うが、社長も承認や代理操作なしで直接変更できる。

共有メンバーは既存アカウントから3人を指定する。新しい社員アカウントを自動で共有メンバーへ追加しない。

### お知らせ・翻訳・初期登録

- 詳細に「この件のお知らせを作成」を置き、既存作成画面へ件名と取り組みへのリンクを引き継ぐ。発信者が宛先・本文を確認して発信する。
- お知らせの確認・対応完了と取り組みの状態は独立させる。
- 画面、日本語・中国語の課題名・説明・節目名・近況の翻訳を初期版から提供する。原文を保持し、翻訳失敗でも保存・共有を成功させ、原文表示と再試行を可能にする。
- 同じ原文の翻訳を再利用する。翻訳保存・応答採用時に対象・原文版・言語・認証主体を照合し、古い応答を破棄する。既存の日報・お知らせ翻訳処理は変更しない。
- 初期登録は基本的に管理担当者が行う。販売基盤、商品準備・販売、販促、資金調達、月次管理などを参考に、必要な項目を順次登録する。社長も同じ画面から変更できる。
- 承認済みモックアップの担当・予定・完了数・近況は表示例であり、本番の実績として初期登録しない。

## 3. 第2段階

保存済みの業務メモに「関連する取り組み」を追加する。標準タグ・個人タグは業務の種類として維持し、取り組みの選択とは分ける。

- 1メモに1取り組み。共有設定・付け替え・解除はメモ本人だけが行える。管理権限で他人のメモを勝手に共有しない。
- 「このメモの本文と、その後の更新内容を3人で共有します。添付資料は含みません」と表示する。
- 日報全体、非選択メモ、添付ファイルは共有しない。
- メモ保存と共有設定は別操作。共有失敗では共有だけ再試行し、メモを再登録させない。
- 紐づけで担当・状態・日報本文を自動変更しない。
- 紐づけは専用領域に保存し、既存workLogsのフィールドやupdatedAtを変更しない。関連先変更だけで日報自動処理や月次再作成判定を起動しない。
- 新規サーバーAPIがリンクと権限を検証し、元メモの現在本文だけを返す。本文を共有用に複製しない。旧画面からの編集・削除も次回取得に反映する。
- 画面を開いた時・戻った時・共有操作後に再取得し、取得時刻と更新ボタンを表示する。

追加APIはsetBusinessWorkLogLink、listBusinessSharedMemos、translateBusinessContent。既存のメモ保存・更新・削除APIや直接読取ルールを拡張して全メモを公開する方式は採らない。

## 4. 実装の分離

- 新画面・型・サービス・サーバー処理は専用モジュールに配置する。
- 新データはテーマ、取り組み、近況・変更履歴、共有メンバー設定、メモリンク、翻訳結果に分ける。
- 既存ファイルの変更は入口、お知らせ作成への任意の初期値、公開登録、追加ルールに限定する。日報画面は第2段階でのみ変更する。
- 読込みは利用画面内に閉じ、失敗・空・読込中を区別する。ログアウトや利用者変更で旧データを消去し、古い通信結果を採用しない。
- 既存Functions名・入力出力・保存形式・過去データは維持する。画面とサーバー双方で有効な新機能停止設定を用意する。
- サーバーは現在の有効アカウント、共有メンバー、操作権限、対象、所有者、原文版を検証する。翻訳キャッシュも権限確認を経由して返す。

各段階で保存失敗、権限拒否、入力消失、翻訳失敗、主要操作への影響を3営業日確認する。利用0件は合格としない。問題時は新機能を画面・サーバーで停止し、必要に応じ直前の画面版へ戻す。取り組み・近況・既存日報の保存データは削除しない。

第1段階の受入条件は、管理担当者と社長が同等の権限で取り組みを管理し、工程表から予定・状態・節目の到達状況を把握でき、3人が近況を共有し、社長が確認・指示を出せること。今回の承認を超える細かな管理項目は利用結果に基づいて別計画で追加する。
