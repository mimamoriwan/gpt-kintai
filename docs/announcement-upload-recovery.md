# お知らせの添付送信エラーへの対処

## 利用者向けの手順

`AppCheck: Requests throttled due to previous 403 error` はアプリ認証の失敗後に再試行が制限されている状態です。PDFを3件添付すること自体が原因ではありません。添付は最大5件・合計20MB、PDF・Word・Excelは1件10MB以下です。

1. 入力済みの件名・本文・宛先・優先度・期限を控えます。
2. ページを再読み込みするか、別タブでアプリを開きます。
3. 入力内容を戻し、資料を選び直して発信します。再読み込みすると未保存の入力と添付の選択は失われます。
4. 再読み込み後も同じエラーになる場合は、連打せず、管理担当者へ発生時刻とエラーを伝えます。

送信結果が不明な通信エラーでは、発信済み一覧を確認してから再送してください。今回の改修は自動でページを再読み込みせず、入力と添付を現在の画面に保持します。ページを閉じた後の下書き保存は含みません。

## 実装上の改善

- 添付送信前にログインとApp Checkを確認し、認証が失敗している間はアップロードを開始しません。
- アップロード完了した資料を1件ずつ画面に保持し、途中で失敗しても再送は残りの資料から続行します。
- 添付送信中・お知らせ発信中の進捗を表示し、送信中のフォーム変更と二重送信を防ぎます。
- App Checkの再試行制限に対して無効な強制更新を重ねず、件数・容量のエラーと区別して日本語・中国語で復旧方法を表示します。

App Check、Storage、Firestore、Functionsの権限設定は変更しません。投稿成功後に応答だけ失われた場合のサーバー側の再送応答改善はこの変更に含みません。

## 管理担当者が再発時に調べる項目

1. ブラウザーの最初の403発生時刻と、App Checkトークン交換APIの応答・reCAPTCHA判定を確認します。SDKのエラーに出る待ち時間から初回時刻を推定できます。
2. FirebaseのWebアプリ登録と配信中のアプリID、reCAPTCHA Enterpriseのサイトキーが一致しているか確認します。
3. reCAPTCHAがSCOREキーであり、本番ドメインが許可されているか確認します。
4. APIキーがApp Check APIへのアクセスを許可しているか確認します。

403の後、Firebase JavaScript SDK 11.10.0はプロバイダー内部で24時間の待機状態を作ります。強制トークン更新でもこの待機状態は解除されません。再読み込みはページの認証処理を作り直しますが、サーバー側の判定が再び拒否されれば失敗します。そのため「再読み込みで必ず直る」とは案内しません。

参照: [Firebase公式のreCAPTCHA Enterprise設定手順](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider)、[Firebase SDK 11.10.0のプロバイダー実装](https://github.com/firebase/firebase-js-sdk/blob/firebase@11.10.0/packages/app-check/src/providers.ts)。
