# 仮パスワードと初回変更の運用

## 利用者の操作

管理担当者が対象の従業員に12文字の仮パスワードを発行する。利用者は登録済みメールアドレスと仮パスワードでログインし、最初に本人だけが知る新しいパスワードを2回入力する。新しいパスワードは6〜128文字で、仮パスワードと同じ値は使えない。入力の前後の空白は削除しない。変更後は新しいパスワードで自動的にログインし直して通常画面へ進む。日本語・中国語の案内を用意する。

仮パスワード発行後、変更完了まで業務API・Firestore・Storageへの通常アクセスを拒否する。本人の利用者情報の取得とパスワード変更だけを許可する。変更完了後も、それ以前にログインしたセッションでは業務を利用できない。本人が設定したパスワードを管理担当者へ通知・保存する機能はない。

Google WorkspaceのメールアドレスをログインIDとして使うが、変更するのはgpt-kintaiのパスワードだけである。

## 対象と保存情報

- 発行対象は既存の有効な従業員。Authと利用者情報のメールアドレス・UID・従業員権限が一致し、パスワード認証を持つことを確認する。新しいアカウントは作成しない。
- `users/{uid}`: `passwordChangeRequired`、`passwordResetId`、完了時の`passwordChangedAt`、`passwordAuthTimeAfter`をサーバーから設定する。既存のUID・権限・勤怠・日報を維持する。
- `passwordSetups/{uid}`: 発行ID、状態、発行日時、期限、ソルトと仮パスワードのscryptハッシュを保存する。クライアントからの読み書きは禁止。変更中は選択されたパスワードのハッシュと処理の占有期限も保存し、完了時にすべてのパスワードハッシュとソルトを削除する。
- `passwordAuthTimeAfter`がある利用者では、業務アクセス時の`auth_time`が完了時刻の秒を厳密に超える必要がある。トークン更新だけでは通過できない。フィールドを持たない既存利用者の認証条件は維持する。

変更開始の期限は発行から24時間。期限切れ後もFirebase Auth自体のパスワードログインは成功する場合があるが、変更手続きと業務利用は拒否する。既に開始した変更処理の同じパスワードでの復旧は期限後も可能。変更APIは5分以内のログインを要求する。

## 配置前の確認

1. 最新の公開コミット・Hosting・Functions・Rulesと候補の基点が一致することを再確認する。他タスクの未公開変更を混ぜない。
2. フロント・Functionsのテストとビルド、Firestore/Storageの3権限のルールテスト、ローカル架空アカウントの一連の変更を確認する。
3. 当該公開の承認と既存の公開列との調整を記録する。実アカウントへの発行は配置完了後に行う。配置途中で発行してはいけない。

この候補は本番`db08caf8bb5dcfeee94dc4d52e211f3ab659ee18`にログイン復旧修正`72792d2e`を含む。今回の変更はフロント、全56業務Callableの認証ゲート、新1 Callable、Firestore/Storage Rules。スケジュール・書込トリガー3件は変更対象外。インデックス・Secret・認証サービスの共通設定は変更しない。

## 配置と発行

承認後、ビルド済み候補から対象名を明示し、新1件と既存56件のCallable、Firestore/Storage Rules、Hostingを配置する。本番コマンドは`--project production`を明示する。更新対象のACTIVEと配信ファイルの一致を確認し、PWA更新案内を確認してから発行する。業務APIのゲートは古い画面にも適用されるため、対象者にアプリ更新・再ログインを案内する。

発行前の読取確認（変更なし）:

```sh
node scripts/reset-initial-password.mjs --project gpt-kintai --confirm-project gpt-kintai --email r.fang@cbc-azabudai.com
```

発行時は上のコマンドに`--apply --credentials-out /絶対パス/認証情報.json`を追加する。保存先は共有・バージョン管理の対象外とし、ファイルは所有者のみ読み書き可能な権限で新規作成する。平文の仮パスワードを標準出力・ログ・文書へ出さない。管理担当者が対象本人へ渡し、変更の完了を確認した後、今回の認証情報ファイルを破棄する。

処理は先に変更必須状態と`issuing`を保存し、Authのパスワード変更後に`required`へ進める。中断時は同じファイルを指定し`--apply --resume`で再開する。別のパスワードで上書きしない。新しい発行は、前回が完了済みか、未使用の`required`が期限切れの場合だけ許可する。

## 失敗時の復旧

- `issuing`: 同じ認証情報ファイルで発行を再開する。利用者は案内があるまで待つ。
- `required`で期限切れ: 管理担当者が新しいファイルで再発行する。
- `changing`: 2分の占有期限後、最初に入力した新しいパスワードで再試行する。Authの変更だけが成功した可能性があるので、新しい別のパスワードへ上書きしない。
- 再ログインが必要: 変更処理をまだ行っていなければ仮パスワードを使用する。変更処理を行った後は、入力した新しいパスワードが有効になっている可能性がある。
- `completed`: 再試行してもパスワードを書き換えず、新しいパスワードでログインを検証する。

パスワードの復元や、変更必須フラグだけを解除する復旧は行わない。発行後に問題が見つかった場合もゲートを維持し、対象者の状態を確認する。発行前なら直前の公開版へ戻せるが、発行後にゲートを持たない旧版へ戻すと保護が失われるため単純な一括ロールバックはしない。

既に端末へ表示・保存された情報や、発行済みの添付ファイル取得URLまで無効化する機能ではない。実クラウド固有の配信・App Check・iPhoneのPWA動作は配置後に別途確認する。

## ローカル統合確認

専用の`demo-`プロジェクトのAuth・Firestore・Functionsエミュレーターを起動して、次を実行する。実ユーザー・実データは使用しない。仮のアカウント・プロフィール・日報と認証情報ファイルは終了時に清掃する。Rulesテストはエミュレーターのデータを消去するので同時実行しない。

```sh
GCLOUD_PROJECT=demo-kintai-password FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:19099 FIRESTORE_EMULATOR_HOST=127.0.0.1:18080 node scripts/test-initial-password-flow.mjs
```

Functionsは既定で`127.0.0.1:15001`。必要なら`PASSWORD_TEST_FUNCTIONS_HOST`でローカルポートを指定する。
